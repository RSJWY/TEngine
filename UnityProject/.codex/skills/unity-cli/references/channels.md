# 操作通道：CLI 与 MCP

同一个 Unity Editor 有两条驱动通道，能力不等价。选错通道不会报错，但会**丢掉证据**或**绕过审批**，所以边界固定，不按方便临时决定。

## 一、能力对照

| 维度 | `workflow.py`（Pipeline CLI） | Unity MCP |
|---|---|---|
| 入口 | `.codex/scripts/workflow.py` | MCP 工具（`mcpforunity://` 资源） |
| 是否留证 | 是，`.codex/runs/<run-id>/report.json` | 否 |
| 退出码语义 | `0` 通过 / `1` 失败 / `2` 阻塞 | 无 |
| 审批链 | 写入需 preview → approve → apply | 无 |
| 工程级互斥 | `.codex/runs/editor.lock` | 不经过该锁 |
| 命令粒度 | 160 条注册命令，44 条只读放行 | 35 个粗粒度聚合工具 |
| 返回形态 | 结构化 JSON，经信封解析 | 结构化对象 |
| 能否作为验收结论 | 能 | **不能** |

MCP 的“成功”只说明传输成功，不代表测试、构建、烘焙、保存真的成功。任何交付结论都必须来自 `workflow.py` 的 run 记录，或明确标注为人工确认。

## 二、什么时候用哪条

| 任务 | 通道 |
|---|---|
| 查 Editor 状态、场景层级、组件属性、Prefab 结构、资源搜索 | MCP（快，不需要审批） |
| 交付前正式验证、留证、跑测试 | CLI |
| 查询必须在 CI / 无人值守下复现 | CLI（MCP 依赖 Editor 侧会话） |
| 核对 Unity API 是否存在、参数签名 | MCP 的反射类工具 |
| 写操作 | 见下方第三节 |
| 改 C# 源码 | **都不用** |

源码一律用文件编辑工具。不要用 MCP 的脚本写入工具、批量执行工具或任意代码执行入口修改源码，也不要用 CLI 的 `write_text_file`。这些入口会绕过编辑与授权规则。

## 三、写操作的硬约束

### CLI 只放行 5 条写入目录

```
build、delete_asset、set_build_settings、set_player_settings、tengine_bake_ugui
```

清单定义在 `.codex/scripts/workflow_lib/unity.py` 的 `MUTATIONS`。**未进入该目录的命令，在 `unity preview` 处直接阻塞**——`add_component`、`create_prefab`、`set_transform`、`save_scene` 这类日常写操作目前都没有审批路径。

需要扩充时，先核实命令的源码实现、风险等级与返回契约，再补目录与回归测试；不要用 query、eval、菜单执行等入口绕过限制。

### 不在目录内又必须写时

走 MCP，并由执行方承担 CLI 本应提供的纪律，四步不可省：

1. **只读查目标**：对象路径、当前值、是否存在、影响范围。
2. **说明字段级改动**：改哪个对象的哪个字段，从什么改成什么，会连带影响什么。
3. **等明确确认**：不把“计划已批准”扩大成“可以顺带保存其他改动”。
4. **单条执行 + CLI 只读复核**：执行后用 `unity query` 读回真实值，不信 MCP 返回的 success。

删除、覆盖、包依赖变更、项目设置变更、平台切换、真实构建：逐项单独确认，一次只做一件事。

### 并发

`.codex/runs/editor.lock` 只保护 CLI 一侧，MCP 不经过它。因此：

- 写操作期间不使用另一条通道；
- 同一时刻只允许一个写入来源，不做并行批量写；
- 跨通道操作按“查 → 写 → 查”串行排列，不交叉。

## 四、禁用项

- 图片/模型/音频/纹理生成类工具：会引入外部生成资产，属于新增资产与依赖，需单独授权，不作为默认能力。
- 菜单执行与任意代码执行入口：等同于绕过授权入口，不作为改写、批量操作或查询的捷径。
- Player 运行结果替代 Editor 验证：Player 必须显式定位路径并校验工作目录。
- 用 MCP 结果覆盖或补齐 CLI 失败阶段：失败就是失败，不能换一条通道重试并声称通过。

## 五、失败时的处理

| 现象 | 处理 |
|---|---|
| CLI 无可连 Editor | 报阻塞，不切换到 MCP 假装完成验证 |
| MCP 返回成功但状态可疑 | 用 CLI 只读命令复核；复核不通过按失败处理 |
| 两条通道状态不一致 | 以 CLI 的 `editor_status` 与 run 证据为准，并说明差异 |
| 写入后结果未知 | 先只读查回真实状态，不重放写入 |
