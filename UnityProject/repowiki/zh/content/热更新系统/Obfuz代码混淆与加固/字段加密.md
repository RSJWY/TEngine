# 字段加密

## 目标

Field Encrypt 不只是改字段名，而是让字段在对象或静态内存中保存密文。对字段的写入会先加密，读取会解密，从而提高 Cheat Engine 等工具直接搜索和修改关键数值的成本。

它是 Obfuz 中运行时成本和兼容风险都较高的能力，默认不应覆盖全部字段。

## 支持类型

官方文档列出主要支持：

- 整数类型；
- float/double；
- bool/char 等可映射的简单值；
- enum；
- 部分结构和数组场景取决于当前实现。

实际支持范围应以当前源码 `FieldEncryptPass` 和样本为准。引用类型、复杂 struct、泛型字段、固定缓冲区、显式布局、volatile、线程同步字段等必须单独验证。

## 实现原理

概念上：

```csharp
public int Gold;
```

会转为类似：

```text
真实存储字段：encrypted_Gold
写 Gold = value
  -> Encrypt(value, ops, salt)
  -> 写入密文字段
读 Gold
  -> 读取密文字段
  -> Decrypt(cipher, ops, salt)
```

Obfuz 会重写待混淆程序集和第 4 类引用程序集中的字段访问。因此程序集分类遗漏会直接破坏字段语义。

## Encryption Level

范围 `1-4`，官方建议默认 `1`。字段每次读取/写入都可能执行转换，高等级比常量加密更容易产生持续开销。

## 默认策略

字段加密通常应采用“默认关闭、明确开启”：

- 通过专用规则匹配少量字段；
- 或使用 `[EncryptField]` 标记与业务语义绑定的关键字段。

适合候选：

- 货币、本地库存镜像；
- 战斗生命、伤害倍率、冷却状态；
- 风控计数和本地完整性标记；
- 关键流程状态机值；
- 离线模式必须保存在内存中的敏感值。

不适合：

- 每帧大量读写的 Transform/动画/物理状态；
- 网络或配置 DTO 的批量字段；
- Unity 序列化字段；
- Burst/DOTS 数据布局；
- 跨 native/managed 边界的布局字段；
- 作为字典哈希、锁或原子操作基础的字段。

## EncryptFieldAttribute

官方提供 `[EncryptField]` 用于字段级显式加密。它可以携带 Scope 等配置，使字段选择不依赖 XML 名称匹配。

优点：

- 保护意图贴近业务代码；
- 类型/字段重命名后不易让规则失效；
- 适合极少量高价值字段。

缺点：

- 在源码中暴露敏感字段意图；
- 需要项目代码引用 Obfuz Attribute；
- 大量使用会污染业务模型；
- 最终虽会移除 Attribute，但原始 DLL/源码仍能看到。

推荐通过自定义业务 Attribute + 生成规则，或集中维护字段清单，降低直接暴露保护语义的风险。

## 专用规则

规则层级：assembly → type → field。关键配置通常是是否加密及 Scope/级别继承。类型名支持通配符，嵌套类型使用 `/`。

示意：

```xml
<obfuz>
  <assembly name="GameLogic">
    <type name="GameLogic.Player.PlayerWallet">
      <field name="Gold" encryptionLevel="Basic" />
      <field name="PremiumCurrency" encryptionLevel="Advanced" />
    </type>
  </assembly>
</obfuz>
```

具体枚举和值以当前版本规则解析器为准。规则为空不应被理解为自动保护全部字段；应检查默认级别和 PassPolicy 的实际结果。

## 与序列化库的兼容

字段加密改变真实字段布局和读写路径。若序列化库直接反射字段或生成直接访问器，可能绕过解密代理、保存密文或无法找到字段。

### Unity序列化

Unity 会持久化字段名和布局。即使 Obfuz 的 Unity 策略尽量排除可序列化字段，也不应对以下字段加密：

- `public` 可序列化字段；
- `[SerializeField]` 字段；
- Prefab/Scene/ScriptableObject 中已有数据的字段；
- Inspector/UnityEvent/动画系统绑定字段。

### Newtonsoft.Json等第三方库

区分：

- property 序列化：经 getter/setter，通常更容易保持加解密语义；
- field 序列化：直接反射真实字段，风险更高；
- 自定义 ContractResolver/代码生成访问器：必须实测。

可用策略：

- 对 DTO 禁用 FieldEncrypt；
- 敏感模型对外只暴露 property；
- 使用显式序列化名称和转换层；
- 保存前导出明文快照，读取后写入加密字段；
- 不让加密内存模型直接承担持久化协议。

## 多线程与原子性

字段读写被展开为多条指令后，原本简单的读写可能不再具备同等原子性。不要对依赖 `Interlocked`、`volatile`、lock-free 或 native 共享内存的字段启用。若属性封装内部有锁，也要确认重写发生在锁内还是锁外。

## 测试清单

1. 初始值、构造器、静态构造器。
2. 自增、自减、复合赋值和 ref/out。
3. 跨程序集读取与写入。
4. property 包装字段。
5. Unity/JSON/二进制序列化往返。
6. 热更新前后字段兼容。
7. 多线程、异常和 domain reload。
8. 真机 IL2CPP 与 HybridCLR 行为。
9. 内存搜索效果和性能基准。
