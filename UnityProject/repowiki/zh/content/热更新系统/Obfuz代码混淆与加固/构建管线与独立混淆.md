# 构建管线与独立混淆

## Player构建自动混淆

Obfuz 的 `Obfuz.Unity.ObfuscationProcess` 实现 Unity `IPostBuildPlayerScriptDLLs`，在脚本 DLL 编译完成后、进入后续 Player/IL2CPP 流程前修改程序集。

`BuildPipelineSettings.enable` 只控制此自动回调；即使关闭，代码仍可主动调用 `Obfuscator` 或 Obfuz4HybridCLR 混淆热更新 DLL。

## 构建事件

官方提供：

- `ObfuscationProcess.OnObfuscationBegin`；
- `ObfuscationProcess.OnObfuscationEnd`。

建议用 `[InitializeOnLoadMethod]` 注册，适合：

- 保存配置快照；
- 构建日志与耗时统计；
- 复制 mapping 到制品目录；
- 检查默认 secret；
- 对混淆后 DLL 做验证；
- 生成渠道水印记录。

独立混淆不会触发这两个 Player Build 事件，若统一发布审计，需在自定义热更新流程中显式调用同类逻辑。

## 原始与混淆程序集

自动流程会把涉及重写的程序集保存为两套：

```text
Library/Obfuz/<BuildTarget>/OriginalAssemblies
Library/Obfuz/<BuildTarget>/ObfuscatedAssemblies
```

包括：

- 真正被混淆程序集；
- 第 4 类仅同步引用的程序集。

这些目录是临时构建缓存，不是长期制品。正式发布应另行归档：配置快照、mapping、最终 DLL 哈希和工具版本。

## link.xml转换

AOT 类型改名后，原始 `link.xml` 中的类型/成员名不再匹配。Obfuz 通过 `IUnityLinkerProcessor.GenerateAdditionalLinkXmlFile` 扫描 link.xml，将原始名称转换为混淆名称并生成附加文件。

需要注意：

- 回调顺序影响其他 Linker Processor 看到哪套名字；
- 动态生成 link.xml 的插件也必须在正确阶段完成；
- 规则保名和 mapping 必须与当前构建一致；
- Obfuz4HybridCLR 对被混淆 AOT 与热更新关系还有额外处理。

## 独立混淆适用场景

- HybridCLR 热更新 DLL 发布；
- 不走 Unity Player Build 的服务器/工具程序集；
- CI 单独生成保护制品；
- 对编译后的第三方/外部 DLL 处理。

官方流程：

1. 使用 `PlayerBuildInterface.CompilePlayerScripts` 或 HybridCLR 命令编译 DLL。
2. 根据 BuildTarget 设置程序集搜索路径。
3. `ObfuscatorBuilder.FromObfuzSettings(...)`。
4. 插入高优先级 search path。
5. `Build()` 并 `Run()`。
6. 从 Obfuz 输出目录复制最终 DLL。

使用 HybridCLR 时官方强烈建议使用 Obfuz4HybridCLR，而不是复制示例自行拼装，因为它还解决 dnlib 冲突、裁剪和多态 DLL。

## TEngine热更新构建链

[BuildDLLCommand.cs](file://Assets/TEngine/Editor/HybridCLR/BuildDLLCommand.cs) 当前流程：

```text
Sync AOT Metadata Manifest
  -> CompileDll(target, developmentBuild)
  -> Copy AOT metadata DLL
  -> Copy hot-update DLL/PDB
  -> ENABLE_HYBRIDCLR && ENABLE_OBFUZ:
       再编译 DLL
       获取 Obfuz4HybridCLR 输出目录
       ObfuscateHotUpdateAssemblies
       对待混淆程序集选混淆目录
       对其他程序集选原始目录
       复制为 *.dll.bytes
```

风险点：

- 混淆分支内再次 `CompileDll(target)` 未传 developmentBuild，应确认不会导致 PDB/产物差异；
- 必须保证输出子目录存在；
- `GetObfuscationRelativeAssemblyNames()` 与 HybridCLR 程序集名一致；
- 混淆后 PDB 是否保留/可用需明确，Release 不应打包原始符号；
- 构建异常时不能静默回退到原始 DLL；
- 最终 `*.dll.bytes` 应检查确实来自预期目录。

## dev/release模式联动

本工程把 `ENABLE_OBFUZ` 定义为 release 模式：

- dev：生成/加载 PDB，PackageNote 记录 `dev`；
- release：期望混淆，禁止残留 PDB，PackageNote 记录 `release`；
- 启动时检查 Exe 与资源包模式一致。

这能防止 dev Exe 误载 release 包或反之，但还应增加“release 构建必须证明混淆产物存在”的硬检查。仅有宏不代表 `Obfuz.asset`、VM、密钥和输出均有效。

## CI发布门禁

Release 构建前应失败阻断：

- Obfuz/Obfuz4HybridCLR 包不可解析；
- 使用官方默认 secret 或 `RandomSeed=0`；
- VM/静态密钥/mapping 缺失；
- `ENABLE_OBFUZ` 与 Build Pipeline 状态不一致；
- 待混淆 DLL 输出缺失；
- 最终 DLL 与原始 DLL 哈希相同且无合理解释；
- mapping 未归档；
- 反射兼容检测存在未豁免错误；
- PDB 或调试 mapping 被放入正式资源包。
