# 程序集分类与依赖处理

## 四类程序集

Obfuz 从“是否被混淆”和“是否引用被混淆程序集”两个维度划分程序集：

| 类型 | 自身混淆 | 引用被混淆程序集 | 配置位置 |
|---|---:|---:|---|
| 1. 被混淆程序集 | 是 | 任意 | `AssembliesToObfuscate` |
| 2. 普通无关程序集 | 否 | 否 | 无需配置 |
| 3. 被混淆程序集的依赖 | 否 | 通常被其引用 | 作为解析依赖搜索，不重写 |
| 4. 不混淆但引用被混淆程序集 | 否 | 是 | `NonObfuscatedButReferencingObfuscatedAssemblies` |

第 4 类是最常见、也最严重的遗漏点。

## 为什么第4类必须重写

### 符号改名

假设 `GameLogic.PlayerData.Gold` 被改为 `$a.$b`。`Launcher` 自身不混淆，但其中 IL 仍引用原来的 `PlayerData.Gold`。如果不把 `Launcher` 加入第 4 类列表，Obfuz 不会更新其中的 MemberRef/TypeRef，最终会在 IL2CPP 转换或运行时出现“找不到原始名称”的错误。

### 字段加密

字段加密会改变字段真实存储形态，并重写对该字段的读写。如果外部程序集仍使用原始 `ldfld/stfld` 语义，就可能读取错误类型、跳过加解密或直接产生无效 IL。因此所有跨程序集字段访问方都必须参与引用重写。

### 其他Pass

调用混淆、属性访问器改名、事件方法改名等也可能要求跨程序集引用同步。正确原则不是“只列直接报错的程序集”，而是从 asmdef/编译程序集图推导完整闭包。

## 本工程当前分类

[Obfuz.asset](file://ProjectSettings/Obfuz.asset) 当前配置：

```yaml
assembliesToObfuscate:
  - GameLogic
  - GameProto
nonObfuscatedButReferencingObfuscatedAssemblies:
  - TEngine.Runtime
  - Launcher
  - Assembly-CSharp
```

该配置表达：

- `GameLogic`、`GameProto` 是 HybridCLR 热更新程序集并被混淆；
- 主包运行时、启动器和默认程序集可能直接引用热更新公开类型，需要同步引用。

但这只是当前快照。新增 asmdef、编辑器生成代码、测试程序集或第三方桥接层后，应重新审计。尤其要检查：

- 主包流程层是否引用热更新类型；
- UI/配置/协议生成程序集是否互相引用；
- 反射注册代码是否被编译进另一个程序集；
- XLua、IOC、序列化生成器、AOT 泛型引用文件的实际程序集；
- 条件编译宏是否在不同平台产生不同依赖图。

## 如何建立依赖图

### 从asmdef开始

读取每个 `.asmdef` 的 `references`。如果 A 引用 B，且 B 被混淆：

- A 也混淆：加入 `AssembliesToObfuscate`；
- A 不混淆：加入第 4 类列表。

### 处理Assembly-CSharp

没有 asmdef 的源码通常进入 `Assembly-CSharp`。它可能通过普通 C# 引用、生成代码或条件编译引用热更新程序集，不能因为“主包不应引用热更新”就默认排除，必须以实际编译依赖为准。

### 间接引用

Obfuz 主要关心 IL 中实际存在的 TypeRef/MemberRef，不是概念上的业务依赖。若 A 只引用 C，而 C 引用 B，A 未直接产生对 B 的元数据引用，通常无需因间接关系进入第 4 类；但泛型签名、继承链和公开 API 可能让 B 出现在 A 的签名中，应以编译产物检查为准。

## DLL形式和项目外程序集

Obfuz 会自动搜索工程内适配当前 BuildTarget 的托管 DLL，包括 Assets、Packages 和 PackageCache。`Additional Assembly Search Paths` 只应在以下场景使用：

- DLL 位于 Unity 工程外；
- 存在多个同名不同版本 DLL，需要显式控制优先级；
- 独立混淆流程使用自定义编译输出目录；
- Editor-only DLL 依赖需要额外搜索 UnityEditor 程序集。

路径不足时常见表现：`AssemblyResolveException`、找不到基类/接口、无法导入 MethodRef，或 Pass 分析到不完整类型。

## Obfuz.Runtime的处理

官方建议开启 `Obfuscate Obfuz Runtime`，不要手动把 `Obfuz.Runtime` 加入普通混淆列表。运行时库中包含解密和映射基础设施，混淆它能提高直接定位核心 API 的成本；同时 Obfuz 内置策略会避免对其函数体进行递归混淆。

需要注意官方 FAQ：在包含原始 `Obfuz.Runtime` 的 Editor AppDomain 中直接加载已混淆且引用“混淆后 Runtime 符号”的 DLL，可能发生 TypeLoadException。验证正式混淆产物应使用 Player/真机，或隔离的纯 DLL 测试工程。

## 常见错误特征

### IL2CPP报告原始名称不存在

典型原因：引用方未加入第 4 类列表。错误信息常出现原始类型、字段、方法、property 或 event 名称。

处理：

1. 定位报错程序集。
2. 确认它是否直接引用被混淆程序集。
3. 加入 `NonObfuscatedButReferencingObfuscatedAssemblies`。
4. 清理并重新生成混淆 DLL、mapping 和 IL2CPP 输出。

### 同名DLL解析到错误版本

处理：将正确目录加入 `Additional Assembly Search Paths` 并确保优先级；不要同时让多个不兼容副本被自动搜索命中。

### Editor可运行、Player失败

可能是 Editor 条件编译下依赖图与 Player 不同，或仅 Player 的某程序集未进入第 4 类列表。必须按目标平台生成并检查 DLL。

## 维护规则

- 每次新增/拆分/合并 asmdef 后审计 Obfuz 程序集配置。
- 每次修改跨程序集公开 API 后跑 IL2CPP 构建，不只跑 Editor Play。
- 对配置生成器、反射注册器和代码生成程序集做单独检查。
- 把程序集分类作为发布检查表和 CI 报告的一部分。
- mapping 异常或 IL2CPP 名称错误时，不要第一时间扩大 `[ObfuzIgnore]`；先修复程序集闭包。
